# 提交规范：什么时机提交、怎么拆、消息怎么写

> 这份文档回答三个问题：**一次提交应该多大**、**什么时候提交**、**提交消息写什么**。
> 本仓库的提交历史就是按这套规范拆的，可以直接对照 `git log --oneline` 看。

---

## 一、核心原则：一次提交 = 一个可解释的变化

判断标准很简单：**能用一句话说清这次改了什么、为什么改**。说不清就说明混了两件事，应该拆。

- ❌ 一次提交塞进「工具层 + Agent + Web + 文档」——出问题没法定位，回滚也回不干净；
- ✅ 一次提交只做一件事：`feat(mcp): 文件工具（含路径沙箱）`。

我们真实的开发顺序，天然就是提交的节奏：

```
1. 能跑起来     → 骨架、依赖、配置
2. 工具能用     → 协议层 → 注册表 → 文件 → 待办 → 天气 → 代码 → 服务器
3. 模型能调工具 → MCP 客户端 → LLM 适配 → 记忆 → 编排循环
4. 人能用得爽   → CLI → Web → 语音
5. 敢改         → 单测 → 评测集
6. 别人能接手   → README → 运行指南 → 代码汇总 → 博文
```

对应到仓库里的提交分组：

| 阶段 | 提交范围 |
| --- | --- |
| 骨架 | 依赖清单、`.env.example`、`.gitignore` |
| 公共层 | 配置读取、脱敏日志、指数退避、错误分类 |
| MCP Server | 协议层 → 工具注册表 → 五类工具 → stdio 主循环 |
| Agent | MCP 客户端 → LLM 适配 → 记忆 → 提示词 → 编排循环 |
| 交互入口 | CLI → 语音 → Web 后端 → Web 前端 |
| 质量保障 | 单元测试 → 评测集与跑分脚本 |
| 交付物 | 代码汇总生成器 → 各类文档 → 博文 |

## 二、提交时机：什么时候按回车

| 时机 | 提交 | 说明 |
| --- | --- | --- |
| 一个模块写完且本地能跑 | ✅ 立刻提交 | 这是最佳时机，代码还在你脑子里 |
| 修完一个 bug | ✅ 提交 | 消息里写清「现象 → 原因 → 修复」 |
| 重构完，测试全绿 | ✅ 提交 | **重构必须与功能改动分开提交**，否则 review 看不清 |
| 一天结束，代码跑不通 | ⚠️ 别提交到主分支 | 开个分支或 `git stash`，别把半成品推进 main |
| 只改了注释/格式 | ✅ 单独提交 | 前缀用 `style:` 或 `docs:`，方便别人跳过 |
| 顺手改了无关文件 | ❌ 拆出来 | 「顺手改的」最容易污染提交历史 |

**黄金法则**：如果这次提交后你需要 `git revert` 它，会不会连带删掉有用的东西？会，就说明该拆。

## 三、消息格式：Conventional Commits 简化版

```
<类型>(<范围>): <一句话摘要，不超过 50 字>

<body>：为什么改（可选，但推荐写）
```

### 类型（前缀）

| 前缀 | 用于 |
| --- | --- |
| `feat` | 新功能、新工具、新模块 |
| `fix` | 修 bug |
| `refactor` | 重构，行为不变 |
| `test` | 只加/改测试与评测 |
| `docs` | 文档、注释 |
| `chore` | 依赖、配置、脚本、脚手架 |
| `style` | 格式、空行、命名，不影响行为 |

### 范围（括号里）

本项目用：`common`（公共层）、`mcp`（MCP Server 与工具）、`agent`（编排与模型）、`cli`、`web`、`voice`、`evals`、`deps`、`docs`。

### 好消息 vs 坏消息

| 坏 | 好 | 差别 |
| --- | --- | --- |
| `update` | `fix(mcp): 路径归一化下沉到服务端` | 说清了改了什么 |
| `修复bug` | `fix(mcp): 修复双重 workspace 前缀导致的幽灵路径` | 说清了现象 |
| `代码` | `feat(agent): 有界自主循环（步数/时间/token/失败四道闸）` | 说清了范围与内容 |
| `改了一堆东西` | 拆成 3 条 | 可回滚、可定位 |

**摘要用祈使句、不加句号、不超过 50 字**；正文写「为什么」，不写「改了哪几行」（那个 `git diff` 自己会告诉你）。

## 四、提交前自检清单

```bash
git status                 # 确认没有多余文件被带上
git diff --stat            # 扫一眼改动量，混进无关文件就撤出来
git add <具体文件>          # 用具体路径，别图省事 git add .
git commit
```

必须确认的四件事：

1. **没有密钥进仓库**：`.env` 在 `.gitignore` 里，提交前用 `git status` 扫一眼确认它没被 `add`；
2. **没有运行时产物**：`.data/`（数据库、日志）已忽略，不要提交；
3. **能编译**：`python -m compileall -q src`；
4. **测试没变红**：`python -m unittest discover -s tests`。

## 五、本仓库的提交历史一览

```bash
git log --oneline --graph   # 看完整历史
git log --stat              # 看每条提交动了哪些文件
```

一条典型的好提交长这样：

```
feat(mcp): 文件工具（读写/列目录/分析，含路径沙箱）

模型给出的路径不可信，必须在服务端把相对路径、绝对路径、
"../" 越权访问都规范到 workspace 内。
同时处理了"workspace/workspace/x.md"这类重复前缀，
避免模型按用户原话拼接导致的幽灵路径。
```

## 六、常见疑问

**Q：一次功能写了三天，中间状态跑不通，怎么提交？**
A：开分支 `git checkout -b feat/xxx`，每天随便提交（消息可以写 `wip:`），完成后用 `git rebase -i` 把 wip 合并成 1–3 条，再合回 main。

**Q：改了 20 个文件的格式，要拆吗？**
A：不用，但必须**单独一条** `style:` 提交，别混进功能改动里。

**Q：提交后发现漏了一个文件？**
A：如果还没 push，`git add 漏的文件 && git commit --amend --no-edit`；已经 push 了就再补一条 `fix: 补充遗漏的 xxx`，别用 `--force`。

**Q：为什么要写正文？反正没人看。**
A：三个月后你自己会看。尤其是 bug 修复，没有「为什么改」的提交等于没有注释。
